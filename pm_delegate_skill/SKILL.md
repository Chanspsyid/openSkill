# PM 工作量盘点与委派分析

## 前置条件

- 工作区已按 `pm_workspace_skill` 初始化；找不到 `workspace.yaml` 时先引导初始化。
- 本 Skill 的分析质量取决于工作区数据完整度。记录明显偏少时（如非终态事项不足 10 条却声称「活很多」），先提醒用户用 `$pm_capture_skill` 把散落的事捞进来，再做盘点——**证据不足时宁可先补数据，不要凭空补齐**。
- `workspace.yaml` 的 `focus.target`（未来重点方向）为空时，先和用户确认并写入，它是委派判断的核心依据。

## 输出规则

- 三种工作模式：**工作量盘点**、**委派分析**、**招人论证**。三者递进：论证依赖委派分析，委派分析依赖盘点；用户直接要后者时，先检查前置产出是否存在且新鲜（7 天内），过期则先重跑前置。
- 所有结论必须基于工作区数据并引用具体 ID；禁止夸大工作量、编造事项——给老板看的材料一旦失真，伤害的是用户的信誉。
- 产出写入 `80_manage/`，文件名带日期：`80_manage/{YYYY-MM-DD}_{类型}.md`。
- 涉及「给老板看」的版本，遵循与简报一致的纪律：先给用户审草稿，确认后才算定稿；发送用 `$pm_send_skill` 或用户手动。

## 工作量盘点

用户说「盘点工作量」「我到底有多少活」时执行：

1. 扫描全部非终态记录 + 指定周期内（默认最近 4 周）到达终态的记录。
2. 统计：
   - 各维度数量：在办需求/缺陷/待办/版本，周期内关闭数；
   - 覆盖项目数、并行推进事项数（同期 in_progress 的数量）；
   - 碎片化指标：P2/P3 小事占比、跨项目切换点数量；
   - 角色分布：哪些事 owner 是本人且无人可替。
3. 输出两个版本：
   - **自用版**：完整数据 + 结论（活集中在哪、碎在哪）；
   - **老板版（草稿）**：事实呈现体量与分布，语气客观，一页以内，结尾接一句「基于此，建议看一下委派分析」的引子。

## 委派分析

用户说「哪些事能分出去」「委派分析」时执行：

1. 逐条评估非终态事项，按四象限归类：

| 归类 | 判断标准 |
|---|---|
| A 必须本人 | 方向决策、对上沟通、跨部门关键接口、focus.target 内的核心 PRD |
| B 可委派（立即） | 流程性、规则明确、失败成本低的事项 |
| C 可委派（需交接） | 有上下文门槛，需要文档化交接后才能分出去 |
| D 应收缩/停掉 | 与 focus.target 无关、价值存疑、架构调整后会消失的事项 |

2. 每条给出：建议去向（未来下属 / 协作方 / 停掉）、交接成本（低/中/高）、不分出去的机会成本。
3. 汇总输出：四象限清单（引用 ID）+ 关键结论：B+C 类共占多少比例——这就是「需要一个人来承接」的量化依据；D 类是和老板对齐收缩范围的谈判清单。

## 招人论证

用户说「帮我准备招人的材料」时执行，产出给老板的论证材料（草稿先给用户审）：

1. **现状**：工作量盘点摘要（引用数据，不渲染情绪）。
2. **可承接清单**：委派分析中 B+C 类事项清单及其工作量占比。
3. **释放精力的去向**：招人后本人精力将投向 focus.target 的哪些上层问题（方向规划、业务突破）——让老板看到的是「投资回报」而不是「减负请求」。
4. **岗位职责草稿**：从 B+C 类事项归纳出的 JD 要点。
5. **过渡方案**：招到人之前，D 类停掉/收缩的止血建议。

## 建议的口径

- 委派判断有拿不准的事项，单独列出来问用户，不要硬归类。
- 给老板的材料里不出现「太累」「干不完」类表述；用数量、占比和机会成本说话。
- 每次委派分析后提醒用户：把结论同步进 `pm_brief_skill` 老板版的「参与点」——让老板参与「分什么、招什么人」的决策，比单方面提请求更容易站在你这边。
