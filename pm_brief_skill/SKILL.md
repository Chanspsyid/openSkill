# PM 工作简报

## 前置条件

- 工作区已按 `pm_workspace_skill` 初始化；找不到 `workspace.yaml` 时先引导初始化。
- 生成双周报前 `workspace.yaml` 的 `biweekly_anchor` 必须有值；为空时先和用户确定锚点周一并写入配置。

## 输出规则

- **先草稿、后派生**是硬规则：必须先生成「本人草稿版」给用户审阅；用户确认或修改后，才能生成老板版/团队版/下属版。严禁跳过草稿直接出受众版本。
- 所有简报先写本地文件，存入 `90_briefs/{周期}/`。本 Skill 自己不做任何发送动作；用户确认定稿后，询问是否用 `$pm_send_skill` 发到飞书，或由用户手动复制发送。
- 取数只依据工作区文件的 frontmatter（`updated`、`created`、`status`）；工作区是 git 仓库时可用 `git log --since` 辅助核对周期内变更，但以 frontmatter 为准。
- 数据不足时如实说明（例如「本周期无决策记录」），不要编造内容。
- 简报中的事项必须引用 ID，方便回查。
- 同一周期重复生成时，先提示已有文件，确认后用版本后缀（`_v2`）另存，不覆盖。

## 周期与文件命名

| 周期 | 触发语 | 时间范围 | 文件名（存 90_briefs/ 对应子目录） |
|---|---|---|---|
| 日报 | 「生成日报」 | 当天（或用户指定日期） | `daily/YYYY-MM-DD_{受众}.md` |
| 周报 | 「生成周报」 | 本周一至今（或指定周） | `weekly/YYYY-Wnn_{受众}.md` |
| 双周报 | 「生成双周报」 | 从 biweekly_anchor 推算的当前双周 | `biweekly/YYYY-Wnn-Wmm_{受众}.md` |
| 月报 | 「生成月报」 | 当月（或指定月） | `monthly/YYYY-MM_{受众}.md` |
| 季报 | 「生成季报」 | 当季（或指定季） | `quarterly/YYYY-Qn_{受众}.md` |

受众取值：`draft`（本人草稿）、`boss`、`team`、`reports`（下属）。

生成前先复述时间范围给用户确认，例如「本期双周报覆盖 2026-06-01 ~ 2026-06-12，对吗？」。

## 取数逻辑

1. 扫描七个维度目录，筛出周期内 `created` 或 `updated` 落在范围内的记录。
2. 按项目分组（frontmatter `project` 字段），无项目的归入「其他」。
3. 统计口径：新增需求/缺陷数、关闭数、版本发布情况、决策数、待办完成率、当前阻塞数。
4. 拉取仍处于过期/阻塞/停滞状态的事项作为风险输入（口径同 `pm_track_skill` 巡检）。

## 草稿版结构（本人）

```markdown
# {周期}简报草稿 {时间范围}

## TL;DR
{3~5 句：本期最重要的进展、最大的风险、下期最关键的事}

## 关键进展（按项目）
### {项目名}
- {进展，引用 ID}

## 决策记录
- DEC-xxx：{决定了什么，影响}

## 数据
| 维度 | 新增 | 推进 | 关闭/发布 |（需求/缺陷/版本/待办 各一行）

## 风险与阻塞
- {ID}：{风险描述，等待谁/缺什么}

## 下期计划
- {从未完成事项和 due 推导，引用 ID}

## 给你的建议
1. 优先级排序：{下期最该先做的 1~3 件事及理由，引用 ID}
2. 风险预警：{要延期的版本、要烂尾的需求、堆积的 P0 缺陷，引用 ID}
3. 沟通建议：{向上该升级/要资源的事、对团队该同步的事、对下属该反馈的事}
4. 焦点对齐：{与 focus.target 无关的在办事项，标为「收缩 / 委派候选」}

## 个人复盘（周报及以上必出）
- 精力去向：本期处理型事务 vs 方向性思考的大致占比（按事项数量和类型估算）
- 卡住模式：本期反复卡住的环节（等审批 / 跨部门 / 信息不全…），引用 ID
- 决策复盘：到复盘日期的 DEC 记录回看结论
```

日报可省略「数据」「决策记录」「个人复盘」段，突出当日核心事项、关键问题、核心决策及其业务影响、明日计划、阻塞。
月报/季报增加「目标回顾」段：对照项目里程碑（70_projects）评估达成情况。

## 受众版本规则

用户确认草稿后，询问需要哪些受众版本（可多选），逐个生成：

- **老板版（boss）**：目标是让老板准确感知你的工作量与价值，并有参与感。必含五段：
  1. **TL;DR**：结果与业务影响导向；
  2. **工作量快照**：本期处理的需求/缺陷/决策/待办数量、覆盖项目数、并行推进事项数——用事实呈现体量，不诉苦、不邀功；
  3. **核心决策与关键问题**：本期关键决策（引用 DEC）、解决的关键问题，以及各自对业务的影响；
  4. **需要你的支持**：明确、可拍板的诉求；
  5. **给老板的参与点**：1~2 个开放的方向性问题或二选一决策，邀请老板给意见——让老板参与进来站在你这边，而不是只被动接收汇报。
  删去执行细节和内部待办；风险只留需要老板知道或拍板的。
- **团队版（team）**：协同导向。保留进展、决策记录（团队需要知道的口径变化）、跨人协作事项、下期计划。删去对上的资源诉求表述。
- **下属版（reports）**：执行导向。按人分组列出其名下事项的状态确认、下期优先级（P 级明确）、对停滞/阻塞事项的反馈或支持承诺。结尾给认可与改进建议各至少一条，语气具体不空泛。

每个受众版本生成后单独给用户过目；用户确认后才算定稿。最后输出所有文件路径清单，并询问是否用 `$pm_send_skill` 发送到飞书（也可以由用户自行复制发送）。

## 建议的口径

- 给本人的建议基于：风险事项、完成率趋势、决策待复盘项（decision 的复盘日期到期）。
- 给老板版里「需要支持」只列用户在草稿确认时认可的项，不擅自加。
- 老板版「参与点」优先从待定决策（DEC 状态 proposed）和方向性问题中选，不拿琐碎问题消耗老板的参与感。
- 给下属的建议必须落到具体 ID 和具体动作，禁止「继续加油」式空话。
