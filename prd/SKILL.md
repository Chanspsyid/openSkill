# 需求文档（PRD）

一套模版，三种模式。所有模式共用同一章节结构（见 [references/prd-template.md](references/prd-template.md)），差别只在填充深度和完成度标记。这样设计的原因：一份思考草稿可以平滑升级为正式 PRD，只需补内容、不需换结构。

## 适用边界：需求文档，不是项目文档

本 skill 只产出**需求文档**——回答"为什么做、做什么、做到什么程度"的文档。以下**项目文档**不适用本模版，用户要的是这类文档时明确说明并退出本 skill：

- 项目计划、里程碑排期、资源分配
- 进度文档、周报、日报
- 会议纪要（纪要可以作为转换模式的**源材料**，但产出物是需求文档，不是整理纪要本身）
- 复盘总结、项目结项报告

判断标准：文档核心是"需求本身"→ 用本 skill；文档核心是"项目怎么推进/推进得怎么样"→ 不用。

## 第一步：判断模式

| 用户信号 | 模式 |
|---|---|
| 给出了源材料：会议纪要、聊天记录、技术方案、旧文档、在线文档链接 | **转换** |
| 说"想法""思考""帮我理一理""还没想清楚"，或内容明显发散未收敛 | **思考** |
| 要为一个明确的新需求立文档 | **初始化** |

拿不准就直接问用户，不要猜。

## 铁律（三种模式通用）

1. **不编造事实。** 数据、指标基线、人名、日期节点、技术结论——用户没提供的一律不填，标 `==待补充：需要什么==`。一份数据是编的、看起来完整的 PRD，比一份满是待补充标记的 PRD 危害大得多：前者会骗过评审、把错误带进开发。
2. **先读再写。** 转换模式必须完整读完所有源材料再动笔；初始化模式先收集信息再生成。
3. **落盘位置先确认。** 生成前问清文档保存到哪里（当前项目目录 / 笔记库 / 在线文档）。如果用户环境有"本地先创建、确认后再同步在线文档"的规范，遵守它。

## 模式一：初始化

为一个明确的新需求从零立文档。

1. **一次性问齐最小信息集**（不要挤牙膏式追问）：
   - 解决什么问题？有什么证据（数据、用户反馈、上级要求）？
   - 为谁做？影响哪些场景？
   - 做到什么程度算成功？有无量化标准？
   - 有无时间节点（发版、活动、承诺）？
   - 已知的方案方向或约束？
2. 用户答不上来的项直接标 `==待补充==`，不要阻塞生成。
3. 按模版生成完整骨架 + 已知内容，标题用 `【草稿】需求名`。
4. 结尾向用户输出一份**待补充清单**，按"缺了它评审过不了"的程度排序。

## 模式二：转换

把已有材料重组为标准需求文档。

1. 完整读源材料；多份材料全部读完再动笔。
2. 逐节把源内容**映射**进模版结构：是重新组织，不是顺序搬运。同一主题散落在源材料多处的，合并到对应章节。
3. 源材料里没有的章节内容，标 `==缺口：xxx==`，不编造。
4. 源材料里有、但模版没有对应位置的内容，放入文末附录，不要丢弃——转换不应损失信息。
5. 源材料本身的链接/路径写进 `# 信源线索`。
6. 完成后向用户输出**转换摘要**：哪些章节有源支撑、哪些是缺口、哪些内容进了附录。

## 模式三：思考

个人思考草稿，帮用户把发散的想法结构化，不追求完整。

- 只写三块：`# 需求背景`、`# 需求目标`（含产品思路）、`# 开放问题`。其余章节不生成，避免空壳章节制造虚假完成感。
- 标题用 `【思考中】主题`。
- **产品思路写成推导树**：用缩进层级表达"问题 → 候选路径 → 分支判断"，被否掉的路径保留并注明否因（保留否因是为了下次不重走弯路）。
- **开放问题清单**是这个模式的核心产出：把用户没想清楚的点显式列出来，每条尽量写成可以拿去问人/查数据的具体问题。
- 允许追问用户 1-2 个最关键的发散问题来帮助思考，但以承接和结构化用户的想法为主，不要替用户做产品判断。
- 想法成熟后升级：改标题为【草稿】，按模版补齐其余章节，进入初始化模式的待补充流程。

## 写作风格（所有模式必须遵守）

风格细节和逐节写法见 [references/prd-template.md](references/prd-template.md)，核心规则：

- **Bullet-first**：以要点列表为主体，缩进层级即逻辑层级；一条 bullet 只说一件事。成段散文只用于定义和原理说明。
- **能写数字不写形容词**："加载时长 4-8s，低配设备 14s"，而不是"加载很慢"。
- **优先级显式标注**：功能块用 `【P0】`/`【P1】` 前缀；裁剪范围要写出来——`【本期不做，后续观察】xxx`，让评审者看见你砍了什么。
- **标记语法**：`==高亮==` 标注待确认项和开放问题；`✅` 标注已确认的边界结论；疑问直接写进文档（如"下载开始有无埋点事件？"）。PRD 是工作文档，开放问题显式化比藏起来有价值。
- **表格**用于三类内容：场景×配置覆盖矩阵、需求项清单（需求项/描述/备注）、埋点字段表。
- **流程图**用 mermaid（flowchart），核心链路一张图，不要为画图而画图。
- **链接就地引用**，不复述被链接文档的内容。

## 文档状态生命周期

标题前缀标注状态，随进展更新：

`【思考中】→【草稿】→【待评审】→【开发中】→【已上线】→【已全量】`（中止则改为`【已搁置】`并注明原因）

## 需要正式评审版时

默认模版是轻量工作风格。当用户要求"正式模版"、需要跨部门评审、或文档要交给不熟悉该项目的人时，改用 [references/formal-review-template.md](references/formal-review-template.md)（含版本信息、变更日志、期次拆解、非功能需求等正式章节）。
